# E11D 射频修复：当前可执行状态

更新时间：2026-08-21（Asia/Shanghai）

本文件只保存能够可靠指导下一步的当前状态。被证伪的旧路线保留为历史证据，但不再作为修复依据。

## 目的

在不破坏本机身份、校准与原厂配置的前提下，使 n78 5G SA 注册、PS 附着和真实数据在真正断电冷启动后可重复、长期稳定。

WebUI 不属于当前修复范围。

## 背景

当前工作基线是 `selector=00 / FSID0` 与已冻结的 v4 QMI ONLINE holder：启动后约 20 秒只发送一次 ONLINE，随后持续持有代理。该生命周期已在多个冷启动样本中表现一致，不再作为故障变量。

模块能够完成真实 n78 无线过程：RACH 成功、RRC 建链、5G Registration Request / Authentication / Security / Accept / Complete 均已出现。故障不是“完全不能发射”或“从未注册”。

注册完成约 17–19.5 秒后，模块内部进入 PWR_SAVE 路径，并由 UE 主动发送 `MO Deregistration Request (SwitchOff=true, reregistration_required=false)`；之后转入 WCDMA/LTE 搜索。

- `sig_path 710 / rfm_device 13 / pll 4 / ant 16` 与 `sig_path 711 / rfm_device 12 / pll 3 / ant 41` 都是实际被使用的合法路径。

### 2. NVTA/IDC 缺口真实存在，但不是已证明的 RF 映射故障

最早可见的同一失败事务为：

```text
NV30016/type10016 精确查询未命中
  → 合法 path/rfm/pll/ant，但 ndr_state=0xFFFF
  → tech18/band78，但 trxDev=0xFFFF
  → No IDC cal data type10016
```

path710 与 path711 均重复该形态；目标捕获没有一次成功的 n78 IDC 对照。

控制流计数为：`RFC cal data location lookup failed` 0 次；tree miss、key 回显与 No-IDC 各 360 次。说明 cal-location 硬失败没有发生，含 `0xFFFF` 的键在查询前已经存在。其具体赋值层仍不可见。

同一 QDB 将 `ndr_state=65535` 明称为 `default NDR data`，所以不能再解释为“设备未建立”。`trxDev=65535` 是非通配查询参数，但缺少匹配枚举定义，不能单凭数值判为非法。

树审计显示 NV30016/type10016=0、NV29650/type10015=0。目标 type 整体缺失已足以解释 No-IDC，无论 `trxDev` 为何都会 miss。因此 `0xFFFF` 不是 No-IDC 的必要根因，也不能据此反推 RFC/TRX 映射损坏。

本地只读搜索索引 211,619 个文件、检查 142 个真实 DIAG/24 个 AP070 trace，没有一份真实进入 n78 TX 且 IDC 成功的健康键对照。2026-08-12 样本只覆盖 RF 初始化/能力声明，未进入 n78 TX/IDC，且不是同一张卡。

### 3. 掉线链由模块内部 PWR_SAVE 发起

目标周期的已确认顺序为：

```text
15:51:25.372215  SD script NEW_ACQ / ACQ_CNT_CHGD
15:51:25.373045  SS preference event → 更新后的 effective mode_pref=NONE → action=PWR_SAVE，state=ACQUISITION
15:51:25.543301  event=0x69 → action=CONTINUE，state=PWR_SAVE（当前 event 名称未验证）
15:51:25.614...  UE 发送 MO Deregistration Request，SwitchOff=true
15:51:25.620922  SD script NEW_ACQ
15:51:25.621518  SD script NEW_ACQ
15:51:25.621519  SS preference event → 更新后的 effective mode_pref=0x1220 → action=ACQ_GWL，limited selection
15:51:25.732...  WCDMA enter_mode
```

第一条是当前日志中最早可见的 PWR_SAVE 指令，而且其完整 payload 直接给出 **SD 更新后的 effective `mode_pref=0`**；第二条确认约 170 ms 后实际处于 PWR_SAVE。网络侧普通 RRCRelease 只释放连接，不能解释此前已经形成的本机停模请求。

六组事件文件共 54 条 `0x26D`：12 条 event 4 全部为 20 字节，其余 42 条全部为 8 字节；event 4 的 offset 8–19 又逐字段吻合旧 `ss_pref` 布局。因此 AP070 的 event 4 高可信是 **SS preference event / `USER_SS_PREF`**，不是旧版枚举数值 4 对应的 `USER_PWR_SAVE_EXIT`。最简单的版本演进解释是旧 `OFFLINE_AMPS` 枚举被移除后编号前移，但精确实现方式仍未证明。

第一条 event 4 的 `ss_pref` 参数为 effective `mode_pref=0x0000`、`band_pref=0x00400000`、`roam=0xFF`、`hybr=0`；后一条为 effective `mode_pref=0x1220`，action 参数同时给出 wildcard PLMN 与 `LIMITED` selection。旧源码证明 `sdcmd_user_ss_pref7()` 先执行 `sdss_pref_update()`，reporter 随后才通过 `sdss_get_mode_band_pref()` 读取并上报更新后的状态，因此这里的 `mode_pref=0` **不是 incoming `cmd->mode_pref` 的镜像**。

当前最强的机制匹配是瞬态 `srv_domain_pref/domain_pref=NONE`：旧 `sdss_pref_update()` 在 domain NONE 时删除 TDS/GSM/WCDMA/LTE 模式分量，AP070 当前 QDB 保留同义消息 `SD_PREF_UPDATE: Mode pref update to %d in domain none`，当前 Clade direct code 又在 `DD052C24/DD052C30` 直接出现 `0x1200` mode mask 与 `bitsclr`。这能用一次短暂 domain 变化解释 **effective mode 0/B1 保留 → PWR_SAVE → SwitchOff → effective mode 0x1220/B1 恢复 → ACQ_GWL limited**，无需假定持久 mode 配置被写成 0。当前代码已经证实该消费机制存在；由于承载目标 QDB 消息的 CM/MMODE PD 没有经本捕获通道交付，`domain NONE` 尚不是运行时直接观测值。

普通 `PS_DETACH` 是已经闭合的直接机制，但不再等同于“本次最可能的外部生产者”。当前 AP070 direct code 已在 `DD254040/DD254044` 直接证实：当前域为 `PS_ONLY(1)` 时，输出/强制域会写成 `0xFF/-1=NONE`；`PS_LOCAL_DETACH(8)` 则保留当前域并绕过 NONE 映射。public producer 审计进一步证明：AT `+CGATT=0` 会显式写 ordinary `6`，DIAG SYS_SEL_PREF 也可显式传入 `6/12`；QMI NR5G full-voice 与 CFCM thermal 不能产生 `6/12`。当前 Ubuntu 没有 AT/DUN/NAS client，holder 只使用 DMS，DIAG logger 也不发送 SYS_SEL_PREF，因此这些外部请求面不能解释本周期的自主掉线。目标事务仍缺少 first PH command 的 client/sub/domain 真值，不能把 ordinary detach 机制本身冒充为已命中的 producer。

当前内部高优先候选已经收敛为 **true-SSIM 不变量被破坏**，但它还不是唯一运行时归因。四份 PolicyMan 配置均声明 `num_sims=1/max_active=1`；合法单卡初始化应把 main/DDS 固定为 AS1 并拒绝 DUAL standby。可是当前代码存在三条只在该不变量失效后可达的 autonomous `NONE` 路径：`DD256A60` 在 main 被错误判为 non-DDS 时把持久 `PS_ONLY/NONE` 投影成运行域 `NONE`；`DCF61044` 在非法 DDS 变化时从旧 DDS 移除 PS；`DCF61844` 在 effective `new_standby=DUAL + same DDS` 时选择名义“另一订阅”，且本地没有验证该订阅是否真实存在/可用，因而幻影 AS2 或陈旧 slot 就可被写成匿名 `SYS_SEL_PREF NONE`。合法 true-SSIM 下三者都不应发生。

静态 caller 已进一步闭合：两个内部 `MSIM_PREF` caller 只重放既有 `phone+0x77` 或 `AUTO/AUTO_NO_TUNEAWAY`，没有发现第三个冷启动 helper 直接写 literal `DUAL=2`；`DD256A60` 的 ONLINE caller 早于注册，subscription-reset caller 则必须由订阅状态命令驱动。它们把范围收窄到 stored standby、SSIM/num_sims、active/available subscription、DDS 或订阅 reset 状态，但不能证明目标周期实际命中了 command 31。ordinary `PS_DETACH=6`、explicit DDS remove-PS 与 persistent-load 仍是并列候选，不能在首次 CM 事务不可见时用静态优先级代替归因。

true-SSIM validator 本身也已定位：current `DCFE00D0` 只返回 `GP+0x25F7` 的缓存 byte，`DCF60104/DCF60110` 在该值为 `1` 时走 standby-pref error `0x37` 拒绝路径，为 `0` 时才继续多卡校验。四份 `1/1` 配置与初始化失败回退 `1/1/1` 只证明预期输入；authoritative device-mode/`nSims` 到这个缓存的 current writer 和首次消费前写入顺序尚未闭合。因此不能静态保证失败周期 validator 看见的是 `1`，也不能把 accessor 直接改成恒真。

五个独立周期中的 `0x7B8 / 0xA05` 已解码为同一次 subscription 0 `IMS` EPC PDN 状态双报；IMS PDN 都在 effective mode 归零/PWR_SAVE **之后约 71.788–75.959 ms** 进入 `DOWN`，随后重新 `COMING_UP`。这证明 teardown 是本机控制链的真实后果，但事件没有 reason、caller、detach type、DDS 或 domain 字段，不能用来区分普通 detach 与 DDS，也不能把 PDN DOWN 当作修补位置。

origination queue 的静态链已被进一步审计。代码中确实存在 `DC00C9C8 -> DC00CA5C -> DD256D40(PS_DETACH_EVAL) -> ph+0x511 -> clear pending -> DCFB0740(FORCE_ORIG)`；但普通 ONLINE/system-selection/PH_OBJ 插入会把 `orig_mode_uptime` 初始化为 `-1`，不会直接创建 `CM_1_CALL_PLUS(term=5)` 非零 deadline。insert 阶段当前直接证实的 `now+4` 仅为 `term=6 / MO_SMS` 特例。`DCFB7E04` 已纠正为 `term=4 / CM_1_CALL` 的 GET_NET/MT-call 延迟写点，不是通用 term5；term5 的当前路径位于 `DCFB7FAC` 后，但具体 add/store 落在 `DCFB7FB4..7FBC` 的构建空洞，只能由同源机制支持，不能冒充当前直接指令。

`cmph_update_orig_param(DCFB7CA8)` 当前直接调用者只锁定为 `cmipcall_p` CM→IMS CALL_END 和 `cmwcall_c` CM→NAS CALL_END。前者属于 voice/VT/emergency；后者理论上可含 legacy GW/PDP PS data call，但没有证据证明本轮 NR IMS PDU/PDN 走这条 legacy 路线。Registration Complete 到 mode0 的 14.128/19.281/19.206/16.855 秒差值也不支持固定 15/20 秒 deadline。orig-expiry 因缺少目标业务前提而降级；由于 CM PD 整体没有经当前 DIAG 通道交付，不能再用“相关日志为 0”作为排除证据。不改 4 秒 hold、共享 queue writer、`DD256D40`、`ph+0x511` 或 FORCE_ORIG。

仍未证明的是哪一条路径在目标事务中实际命中。此前“MMOC wake cycle”结论已经撤销。offset 4 的固定 `0x10` 不能命名为 pwr-save reason，因为旧 reporter 对 PWR_SAVE action 不复制该参数且局部缓冲区未清零；offset 8 的 `reason` 字节同样未被旧 reporter 写入，不能解码；`0x783` 也只证明 NEW_ACQ，不携带原因。

主机侧 `ModemManager` 虽在 15:51:09 启动，但 Foxconn 插件被禁用，QMI/DIAG/ADB 节点没有 `ID_MM_CANDIDATE`，它没有创建 modem，并把该 PCI 设备标为不受任何插件支持；`/dev/mhi_QMI0` 的唯一直接持有者是静默 qmi-proxy。该时间重合已排除为可行 QMI 控制源，不安排停服实验。

### 4. 两个未决问题必须分开

1. **NVTA/IDC 问题：** type10015/10016 缺失究竟是允许的可选校准形态，还是本卡丢失了只能由同卡工厂标定产生的数据；当前不能以 `0xFFFF` 猜映射补丁。
2. **生命周期问题：** 是谁产生了普通/FORCE `PS_DETACH`、DDS/standby role transition、显式 `SYS_SEL_PREF NONE`，或（仅在 SGLTE/动态 capability 异常时）使 requested domain 与 stack/PolicyMan capability 的交集变成 NONE；orig queue 只有在闭合同一 act_id 的 CALL_END→term5→expiry 后才重新升级。event 4 只记录 SD 更新后的 effective mode。现有 MM/GMM 状态只能证明 no-cell/search/limited-service 上下文，不能独立区分 `NO_SYS/NO_SRV`。

IDC 错误在 Registration Complete 之前已经出现，并在 SwitchOff 前再次出现；二者存在时序相关性，但当前证据尚未证明 IDC 失败直接触发 PWR_SAVE/SwitchOff。

### 5. 现有 DIAG 的可见性边界

QDB 中存在可直接打印 SD pwr-save reason、`cmregprx` NO_SYS 转换以及 PolicyMan/CM/SD preference 更新的目标消息，包括 CM command/current domain、PS-detach forced domain、CMMSC domain×capability 结果、SD incoming domain、domain-none mode update、PolicyMan capability change 与 subscription available/not-available。但原始捕获的 QSR code-address 前缀只有 `00/BD/D8/D9/DA`，没有承载这些 CM/MMODE 记录的 `DC/DD/FA` 地址族；映射时间线中的 CM/CMMSC 行数也为 0。故这些记录是 **整个 PD 未被当前通道交付**，不是逐地址“启用后未命中”。任何 `DCF61044/DCF61844/DD25415C` 等零计数都不能用于证明路径未执行。

PWR_SAVE 前两秒到注销后的可交付窗口仍只有 RF/NV/RF-thermal、mutils_security 与已知协议/event 正证据。`0x98` 只是 MULTI_RADIO 包装，离线解包没有隐藏 QTrace；继续扩大相同 legacy F3 掩码或重复同类冷启动不会补出缺失的 CM PD。当前被动 DIAG 的边界应写成“无法观察首次 CM transaction”，而不是“观察后确认它没有发生”。

后续离线 Ghidra 审计纠正了地址域：本组 DCC/DD/DC QDB 地址不应减 `0x31000000`，而应原样映射到 `AP070_clade_D8000000.elf` 的 `0xD8000000..0xDD3FFFFF` 可执行段。direct code 已直接证实普通 `PS_DETACH` 的 `PS_ONLY(1)->NONE(0xFF/-1)`、`PS_LOCAL_DETACH(8)` 保留当前域并绕过 NONE 映射、DDS remove/add-PS 两侧及 SD domain-none mode-mask 消费路径。它证明机制存在，却不能补造目标事务缺失的 caller/参数，也不构成二进制 patch 授权。旧 AB/AC relocation 报告已标记为被 `analysis/boot_diag_decisive_20260821/ap070-domain-pref-direct-static-audit.md` 取代。

## 已证伪或废弃的路线

- `selector=02 / FSID2`：真冷启动后 offline；废弃，不能再切换。
- “两颗 2B69 本来不存在/没有闭合”：被当前只读扫描与 AP070 官方拓扑反证。
- 删除、压缩或重编号 logical ASIC4/5：曾导致无频段、`rfm_init=0`；废弃。
- 修改公共 `rfm_device_tbl` row12/13、把字段 0/1 改成 3/4、强制把 `0xFFFF` 写成 0/1：`ndr=65535` 已知是 default NDR，且 type 整体缺失；该改法没有因果依据，禁止。
- 跨卡覆盖 NV29650/30016、伪造 type10015/10016 IDC 节点：没有同卡合法精确键与校准来源；禁止。
- 把 ONLINE 提前/延后、改 holder 生命周期、重复 NAS automatic register：多组时序和受控实验已否定其作为有效修复变量。
- 把网络 RRCRelease、WDS 拨号或持久化 T3346 当作直接根因：已被时序或只读证据排除。
- 把 event 4 当作 `USER_PWR_SAVE_EXIT`，进而追 MMOC wake cycle：20 字节 payload 已反证该解释；废弃。
- 把 event 4 的后 12 字节称为 AP070 未知扩展：旧 20 字节结构与 `ss_pref` 字段已逐项吻合；废弃。
- 把 event 4 的 `mode_pref=0` 当作 incoming command 原值：reporter 在 preference update 后读取 effective state；废弃。
- 在 SD 强制 `mode_pref=0x1220`、删除 domain-NONE 过滤、绕过 mode-none/PWR_SAVE 脚本或屏蔽 SwitchOff：会破坏合法离线、无订阅、SIM 去激活和真正 PS detach 的安全语义；禁止。
- 扩大相同 legacy F3 掩码、重复同类冷启动：受到日志实现边界限制，不再提供新信息。
- 依据健康样本的 RF-init 相似性直接推导健康 n78 IDC 键：该样本没有证明实际进入与目标相同的 n78 TX/IDC 查询，不能承担此结论。

## 当前不确定性与下一步

当前没有经过证据审查、可以安全写入模块的单变量 patch。下一步只接受能够提高确定性的两条路线：

1. **取得首次改变 service-domain 的 CM 事务，而不是继续普通冷启动**：第一层必须同时得到 `command id / caller 或 callsite / sub / client / 输入 srv_domain / handler 输出 domain / detach flag`。若是 command `0x1F/MSIM_PREF`，再读取 input/effective standby、active-sub mask、subscription availability、runtime SSIM/可靠 num_sims、command/current DDS、stored user/internal standby；若是 `DD256A60`，再读取 callsite、AS_ID、DDS、persistent domain、`ims_for_nondds` 与 subscription-reset 命令类型。若 first producer 是单卡被错误判为 non-DDS，就恢复 `default_data_subs == main AS1`；若是单卡被错误送入 DUAL，就在 standby 命令进入 MSIM processor 前按可靠、不会被错误运行态污染的 `num_sims` 拒绝或归一化，并在 remove-other 点要求 other subscription 确实 real/provisioned/available/active；不能只检查一个可能被错误命令自己置位的 `active_subs` bit。若首次事务是 ordinary enum6，则只修唯一 caller，不能用 SSIM guard 替代真正归因。只有唯一上游条件闭合后才形成单变量方案；不在 CMMSC/SD 边界钳制，也不全局屏蔽合法 `PS_DETACH/NONE`。MCFG 没有目标事务附近的 refresh 正证据，不据此修改。
2. **单独判断 IDC 缺口**：从当前授权范围之外取得同硬件、同 AP070 软件、真实进入相同 n78 TX/IDC 的健康被动 trace及其树 type 分布；本地 142 个真实 DIAG 已搜索完，没有候选。IDC 不再阻塞生命周期根因的继续定位。

在拿到其中之一前，不做猜测性修复，也不要求再次冷启动。拿到直接证据后，先形成并离线审查唯一单变量方案；只有审查通过，才执行一次真正断电冷启动并按以下条件验收：

- MHI/QMI 正常重新枚举，holder 只产生一个稳定周期；
- n78 RACH/RRC/Registration 成功；
- 若直接证据证明 IDC 节点为本卡必需项：查询使用可追溯的同卡校准数据且不再 No-IDC；否则不把 default `0xFFFF` 本身当作失败条件；
- 不再发生本机 PWR_SAVE → SwitchOff 注销链；
- PS 附着与真实数据在观察窗内持续稳定。
